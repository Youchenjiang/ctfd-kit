## 🧩 第一動：底層機制解剖——進程、服務與排程的底層真相

黑客可以竄改 `ps` 或 `top` 的輸出，但他們**無法欺騙 Linux 核心維護的 `/proc` 檔案系統**。任何活著的進程，其靈魂都刻在 `/proc` 之中。

### 1.1 `/proc/[pid]/` 核心進程鏡像解構

在 Linux 中，「一切皆檔案」。當一個進程被創建（`fork`/`execve`）時，核心會在 `/proc` 下以其 PID 命名一個虛擬目錄。當懷疑某個進程是惡意程式時，**直接去 `/proc/[pid]/` 查戶口**：

```
/proc/[pid]/
  ├── exe        : ★ 符號連結，直接指向硬碟上的「真實二進位執行檔」！（就算黑客把檔名改成 [kworker]，這裡也現形！）
  ├── cwd        : 符號連結，指向該進程當前的工作目錄（常為 /tmp, /dev/shm, /var/tmp）。
  ├── cmdline    : 啟動該進程時傳入的「完整命令列參數」（以 \0 分隔）。
  ├── environ    : 該進程運行時繼承的所有環境變數（常藏有被竊取的 API Key 或 LD_PRELOAD 惡意路徑）。
  ├── fd/        : 目錄，列出該進程打開的所有檔案描述符（包含網路 Socket 與正在讀寫的檔案）。
  └── maps / mem : 該進程的記憶體映射段（可用於記憶體取證與提取解密後的 Payload）。
```

---

### 1.2 systemd 服務單元（Service Unit）與啟動階層

現代 Linux 全面採用 `systemd` 作為 PID 1 的初始化系統。攻擊者最喜歡利用 `systemd` 建立開機自啟或崩潰自動重啟的後門：

```
[黑客最常植入的 3 大 Systemd 目錄]
1. /etc/systemd/system/           : ★ 系統管理員手動安裝的服務（優先級最高，黑客首選藏匿點！）
2. /run/systemd/system/          : 運行時動態服務（重開機自動消失，黑客用於記憶體暫存）
3. /lib/systemd/system/ (或 /usr): 系統預設套件安裝的服務（黑客常在此竄改合法服務）

[惡意 Unit 檔案的致命欄位]
[Unit]
Description=System Core Diagnostic Service   <-- 偽裝成系統核心服務
After=network.target                         <-- 網路連線建立後啟動

[Service]
Type=simple
ExecStart=/dev/shm/.miner/xmrig -c config    <-- ★ 真實執行的惡意木馬路徑！
Restart=always                               <-- ★ 殺掉立刻重啟！（無限復活之謎）
RestartSec=5s

[Install]
WantedBy=multi-user.target                   <-- 設定開機隨系統自動啟動
```

### 1.3 Crontab 的 6 大隱秘藏匿點

很多分析師以為排程只在 `crontab -l` 裡，這導致了大量的後門漏網之魚。Linux 總共有 **6 個排程讀取位置**：

```
[Linux 排程完整掃描面]
├── 1. /var/spool/cron/crontabs/ (或 /var/spool/cron/) : 各使用者的私有排程（crontab -l 查到的地方）
├── 2. /etc/crontab                                  : 系統全域主排程檔
├── 3. /etc/cron.d/                                  : ★ 軟體獨立排程目錄（黑客最愛在這裡放自定義腳本）
├── 4. /etc/cron.hourly/                             : 每小時自動執行的腳本目錄
├── 5. /etc/cron.daily/                              : 每天自動執行的腳本目錄
└── 6. /etc/cron.weekly/ & /etc/cron.monthly/        : 每週/每月執行的腳本目錄
```

## 🧭 第二動：解碼意圖——進程與持久化異常速查表

在排查高負載或可疑主機時，你該如何依據現場跡象精準判定攻擊手法？

### 2.1 Linux 進程與排程異常速查表

| 進程與排程特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **`ps` / `top` 看不到高耗能進程，但系統 Load 極高** | **Rootkit 或 `LD_PRELOAD` 進程隱藏**：<br>攻擊者在 `/etc/ld.so.preload` 載入了惡意動態庫，攔截了 `readdir` 系統呼叫，使 `ps` 自動忽略惡意 PID。 | • **影響**：主機已被植入核心級或用戶態 Rootkit。<br>• **優先級**：緊急（檢查 `/etc/ld.so.preload` 並使用靜態編譯工具）。 |
| **進程名稱帶中括號（如 `[kworker/0:1]`），但母進程非 kthreadd** | **進程名稱偽裝（Process Masquerading）**：<br>黑客修改進程的 `prctl(PR_SET_NAME)` 或竄改 `argv[0]`，將用戶態惡意程式偽裝成核心線程（Kernel Thread）。 | • **影響**：欺騙管理員眼球，逃避一般排查。<br>• **優先級**：高（比對 `/proc/[pid]/exe` 是否為空，核心線程無實體二進位檔）。 |
| **殺掉進程後，數秒或 1 分鐘內立即以新 PID 復活** | **Watchdog 守護進程、Cron 或 systemd 重啟**：<br>存在雙進程守護（Dual Process）、systemd `Restart=always`，或 Cron 每分鐘輪詢重新拉起木馬。 | • **影響**：單純 `kill` 完全無效，攻擊持續。<br>• **優先級**：高（必須先暫停進程 `SIGSTOP`，拔除啟動源後再終止）。 |
| **執行檔位於 `/tmp`, `/dev/shm`, `/var/tmp` 且已被刪除（deleted）** | **無檔案或臨時目錄執行（Fileless Execution）**：<br>黑客在記憶體檔案系統（`tmpfs`）執行二進位檔後立即 `rm` 刪除本體，企圖規避硬碟掃描（但在記憶體中持續運行）。 | • **影響**：主機正運行惡意 Payload。<br>• **優先級**：高（透過 `/proc/[pid]/exe` 逆向復原該二進位檔）。 |
| **Crontab 內容包含 Base64 編碼、`curl | sh` 或 `wget`** | **自動化拉取惡意腳本（Remote Payload Stager）**：<br>定時連線黑客公網伺服器，下載最新的挖礦程式或反彈 Shell 腳本並靜默執行。 | • **影響**：永久性後門與內網感染源。<br>• **優先級**：高（立即註解該排程並阻斷外部下載 IP）。 |

## 💻 第三動：現場追兇——Linux 現場終端排查指令

身為現場調查員，你必須掌握繞過黑客偽裝、直擊真相的核心指令庫。

### 3.1 戳破進程偽裝——深入 `/proc` 查驗

#### 步驟 1：找出在臨時可寫目錄中運行的可疑進程
```bash
# 檢查有哪些進程的執行檔位於 /tmp, /dev/shm 或 /var/tmp
ls -l /proc/*/exe 2>/dev/null | grep -E "(tmp|dev/shm|var/tmp)"
```

#### 步驟 2：揪出已被刪除但仍在記憶體中狂跑的幽靈進程
```bash
# 篩選帶有 (deleted) 標記的執行中檔案（黑客反取證常見特徵）
ls -l /proc/*/exe 2>/dev/null | grep "(deleted)"
```

#### 步驟 3：神仙難救的「進程逆向還原術」
若黑客已經把 `/dev/shm/.miner` 刪除了，你該如何拿到樣本？**從記憶體直接拷貝還原**：
```bash
# 只要進程還在運行，直接從 /proc/[pid]/exe 複製出來即可完整復原惡意執行檔！
sudo cp /proc/18422/exe /root/recovered_malware.bin
chmod 700 /root/recovered_malware.bin
sha256sum /root/recovered_malware.bin  # 計算雜湊進行威脅情資比對
```

#### 步驟 4：戳破 `[kworker]` 核心線程偽裝
```bash
# 真正的 Linux 核心線程，其 PPID（母進程）必為 2 (kthreadd)，且 /proc/[pid]/exe 為空
# 找出所有名稱帶中括號但 PPID 不為 2 的冒牌貨！
ps -ef | awk '$3 != 2 && $8 ~ /^\[.*\]$/ {print "🚨 偽裝進程: PID " $2 ", 命令: " $8}'
```

### 3.2 systemd 惡意服務單元全面清查

#### 步驟 1：列出所有開機自啟動（enabled）的非官方服務
```bash
# 查看所有已啟用的服務，排除系統核心與常見套件
systemctl list-unit-files --type=service --state=enabled | grep -Ev "(systemd|kernel|apparmor)"
```

#### 步驟 2：檢查最近 7 天內新增或修改過的 service 檔案
```bash
# 檢查最容易被藏後門的目錄，按時間排序
find /etc/systemd/system/ /lib/systemd/system/ -name "*.service" -mtime -7 -ls
```

#### 步驟 3：徹底停用並粉碎惡意 systemd 服務
```bash
# 假設惡意服務為 badservice.service
sudo systemctl stop badservice
sudo systemctl disable badservice
sudo rm -f /etc/systemd/system/badservice.service
sudo systemctl daemon-reload           # 重整 systemd 狀態
sudo systemctl reset-failed            # 清除失敗標記
```

### 3.3 Crontab 6 大目錄地毯式掃描

千萬不要只打 `crontab -l`！直接下這行神級 Bash 指令，瞬間快篩全機所有排程目錄：

```bash
# 1. 檢查所有系統層級排程檔案內容
head -n 1000 /etc/crontab /etc/cron.d/* /etc/cron.hourly/* /etc/cron.daily/* 2>/dev/null | grep -E -v "(^#|^$)"

# 2. 檢查所有使用者的私有排程（spool 目錄）
sudo ls -la /var/spool/cron/crontabs/ 2>/dev/null
sudo cat /var/spool/cron/crontabs/* 2>/dev/null

# 3. 搜尋排程中帶有可疑下載關鍵字的指令（curl, wget, python, base64）
grep -Eri "(curl|wget|python|sh\s|bash\s|base64|nc\s)" /etc/cron* /var/spool/cron/ 2>/dev/null
```

在 Linux 伺服器中，備份工具（如 `rsync`、資料庫備份）、日誌輪替（`logrotate`）也會出現在排程中。你該如何一眼看穿？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | CPU 負載突破異常閾值、向未知公網 IP 建立持續長連線，或排程檔案被寫入。 |
| **Q2. 來源路徑**（執行檔存放在哪裡？） | 是正規系統路徑（`/usr/bin`, `/usr/sbin`），還是臨時目錄（`/tmp`, `/dev/shm`）、隱藏目錄（如 `/var/tmp/.hide/`）？ |
| **Q3. 執行權限**（進程運行的使用者是誰？） | 是特定業務帳號（如 `postgres` 執行備份），還是由 `root` 執行未知的小型腳本？ |

| **Q7. 重啟特徵**（被殺掉後的行為？） | `kill` 之後是否立即由未知母進程重新孵化？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 凍結進程（`kill -STOP`）；2. 提取樣本取證；3. 移除 systemd/cron 啟動項；4. 永久刪除執行檔。 |

## 🛡️ 第五動：連根拔除與加固 SOP (Mitigation & Hardening)

當面對具有「無限復活」特徵的頑固惡意進程時，錯誤的處置順序會導致木馬持續死灰復燃。請嚴格執行以下 **「四步封印法」**：

### 1. 第一步：先「凍結」而非「殺死」（SIGSTOP 魔法）
如果你直接下 `kill -9`，守護進程會在 0.1 秒內偵測到進程死亡並重新生成一個新 PID，導致你疲於奔命。正確做法是將其進程凍結在記憶體中：
```bash
# 發送 SIGSTOP 訊號，強制暫停該進程所有 CPU 與網路活動，但保留其 PID（守護進程以為它還活著！）
sudo kill -STOP <PID>
```

### 2. 第二步：斬斷所有自啟動根基（Disarm Launchers）
在木馬被凍結的時間窗口內，迅速清除所有自啟動項：
```bash
# 1. 註解或刪除 Crontab 惡意項目
sudo rm -f /etc/cron.d/malicious_cron /var/spool/cron/crontabs/<user>

# 2. 拔除 systemd 惡意服務
sudo systemctl disable --now badservice.service
sudo rm -f /etc/systemd/system/badservice.service
sudo systemctl daemon-reload
```

### 3. 第三步：消滅進程與執行本體（Eradicate Binary）
此時再將被凍結的進程徹底殺死，並刪除實體檔案：
```bash
# 徹底殺死凍結的進程
sudo kill -9 <PID>

# 刪除實體二進位檔案
sudo rm -f /path/to/malicious_binary
```

### 4. 第四步：設定系統檔案不可變屬性（Immutable Flag）
為了防止黑客透過其他隱密通道再次篡改 Crontab 或注入預載入庫，使用 `chattr +i` 加鎖：
```bash
# 將核心排程檔案與預載入檔案設為「連 Root 也無法修改/刪除」的鎖定狀態
sudo chattr +i /etc/crontab /etc/ld.so.preload 2>/dev/null
```

## 📋 過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能回答，代表你已具備處理 Linux 惡意程式現場應變的能力：

- [ ] **Q1**：如果一個進程在 `ps aux` 中顯示為 `[kworker/0:0H]`，你該如何用 `/proc` 檔案系統快速判定它到底是真的 Linux 核心線程，還是黑客惡意偽裝的用戶態程式？
- [ ] **Q2**：為什麼黑客把位於 `/tmp/.malware` 的二進位檔案執行起來後立刻執行 `rm -f /tmp/.malware`？身為藍隊取證人員，你在磁碟上已經找不到這個檔案了，該如何從系統中完整提取出這個惡意程式二進位檔？
- [ ] **Q3**：在 systemd 服務單元中，`Restart=always` 與 `ExecStartPre=` 經常被黑客用來做什麼？如果你只刪除了二進位檔案卻沒執行 `systemctl daemon-reload`，會發生什麼事？
- [ ] **Q4**：面對具備「雙進程守護（A 死了 B 重啟 A，B 死了 A 重啟 B）」特徵的頑固木馬，為什麼下達 `kill -9` 往往無濟於事？在指令層面你該如何破解這種死鎖局面？
- [ ] **Q5**：黑客若在 Linux 系統中配置了 `/etc/ld.so.preload`，其在作業系統底層的作用是什麼？這為什麼會導致你打 `ls`、`ps`、`netstat` 看到的都是被過濾過的「假象」？
