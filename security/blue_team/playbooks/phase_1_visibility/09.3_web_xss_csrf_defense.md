> **情境帶入**：  
> 週四上午 10:40，公司內部管理後台突然出現不可思議的「靈異現象」：

> 
> 與此同時，資安告警中心接連收到數十位 VIP 會員回報：「我的帳號明明開啟了高強度密碼，也沒有輸錯密碼，但剛才點擊了客服在在線聊天室發送的一個退費連結後，我的帳號 Session 就被陌生人從境外 IP 登入劫持了！」  
> 
> Web 開發團隊困惑地說：「我們的資料庫根本沒有被 SQL 注入，伺服器檔案也沒有被竄改，黑客到底是在哪裡動的手腳？」

> 你打開瀏覽器開發者工具（F12）與 WAF 封包：  
> - 在客服工單內容中，赫然夾帶了一段未經 HTML 實體轉義的惡意 JavaScript 代碼：

> - 而在另一個重置管理員權限的表單中，完全沒有包含任何 **CSRF 防禦權杖（CSRF Token）**，黑客利用誘導點擊，讓客服主管的瀏覽器「借刀殺人」，帶著合法的 Cookie 向後端發起了越權操作！  
> 
> 這是典型的 **跨站腳本攻擊（XSS - Cross-Site Scripting）** 與 **跨站請求偽造（CSRF - Cross-Site Request Forgery）**！

## 🧩 第一動：底層機制解剖——瀏覽器的同源策略與背叛

理解 XSS 與 CSRF 的本質區別，是每個藍隊分析師的基石功力：**XSS 是「黑客利用漏洞在受害者瀏覽器中執行惡意腳本」；而 CSRF 是「黑客利用瀏覽器自動攜帶 Cookie 的特性，冒充受害者發起合法請求」**。

### 1.1 XSS 的三大物理型態

```
[XSS (跨站腳本攻擊) 三大分類]
├── 1. 反射型 (Reflected XSS)
│      • 機制：惡意代碼包含在 URL 參數中，點擊惡意連結後，後端將參數直接「反射」回前端頁面執行。
│      • 特徵：不經過資料庫持久化，誘騙特定受害者點擊專屬連結。
│
├── 2. 儲存型 (Stored XSS) - 【最危險！】
│      • 機制：惡意代碼被寫入伺服器資料庫（如留言板、使用者名稱、客服工單）。
│      • 特徵：任何正常使用者存取該頁面時，惡意代碼皆會從資料庫撈出並在瀏覽器執行（大規模感染）。
│
└── 3. DOM 型 (DOM-based XSS)
       • 機制：惡意代碼不經過後端伺服器！完全由前端 JavaScript（如 location.hash）直接取出並寫入 DOM。
       • 特徵：後端 Access Log 完全看不到 Payload，隱蔽性極高！
```

---

### 1.2 CSRF（跨站請求偽造）的「借刀殺人」模型

CSRF 成立的物理條件只有一個：**瀏覽器在跨站發起請求時，會自動且強制地帶上目標網站的 Cookie！**

```
[受害者瀏覽器]                                              [正規銀行網站 bank.com]
      │                                                               │
      │ 1. 登入 bank.com，取得身分憑證 (Cookie)                        │
      │ ────────────────────────────────────────────────────────────> │
      │                                                               │
[惡意釣魚網站 evil.com]                                               │
      │                                                               │
      │ 2. 受害者被誘導點擊 evil.com 頁面                             │
      │    evil.com 包含一行隱藏表單:                                 │
      │    <img src="http://bank.com/transfer?to=attacker&amount=1000"> │
      │                                                               │
      │ 3. 瀏覽器自動向 bank.com 發送請求，並自動附帶 bank.com 的 Cookie! │
      │ ────────────────────────────────────────────────────────────> │
      │                                                               │
      │ 4. bank.com 看到合法 Cookie，誤以為是受害者本人操作，成功轉帳！   │
      │ <──────────────────────────────────────────────────────────── │
```

## 🧭 第二動：解碼意圖——XSS 與 CSRF 異常速查表

在分析 HTTP 流量或前端日誌時，你該如何依據特徵辨識攻擊？

### 2.1 XSS 與 CSRF 異常速查表

| 請求與標頭特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **參數包含 `<script>`, `onerror=`, `onload=`, `javascript:`** | **經典 XSS 腳本注入 (HTML Tag Injection)**：<br>攻擊者企圖在網頁 DOM 中插入並執行自定義 JavaScript，常用於竊取 Cookie 或進行頁面釣魚。 | • **影響**：使用者工作階段遭劫持。<br>• **處置優先級**：高（WAF 攔截並通知修補 HTML 轉義）。 |
| **參數包含 `<svg/onload=alert(1)>` 或 `<img src=x onerror=...>`** | **繞過過濾之事件處理器注入 (Event Handler Bypass)**：<br>黑客利用 HTML5 標籤與內聯事件監聽器，規避簡單的 `<script>` 關鍵字過濾。 | • **影響**：防禦規則被突破。<br>• **處置優先級**：高（改用上下文關聯轉義函式庫）。 |
| **敏感 POST 操作（轉帳/改密碼）完全缺少 CSRF Token 欄位** | **缺乏 CSRF 防禦機制 (Missing Anti-CSRF Token)**：<br>後端 API 僅仰賴 Cookie 進行身分鑑別，未引入不可預測的隨機防偽 Token。 | • **影響**：極易遭受第三方釣魚網站發動越權操作。<br>• **處置優先級**：高（強制引入 Anti-CSRF 標頭或 Token）。 |
| **敏感請求的 `Referer` 或 `Origin` 標頭來自未知名第三方網域** | **跨站請求偽造進行中 (CSRF In-Flight Execution)**：<br>使用者正在存取惡意外部網站，該網站正跨站向本伺服器發起 API 呼叫。 | • **影響**：受害者瀏覽器正在被當作跳板。<br>• **處置優先級**：高（在後端嚴格校驗 Origin/Referer 網域）。 |
| **Cookie 設定中缺少 `HttpOnly` 標記** | **Cookie 防護基線缺失 (Insecure Cookie Attribute)**：<br>Cookie 允許被客戶端 JavaScript 透過 `document.cookie` 讀取，為 XSS 竊密大開方便之門。 | • **影響**：一旦發生 XSS，Session 必遭秒殺竊取。<br>• **處置優先級**：中至高（在伺服器配置中強制補齊 HttpOnly）。 |

## 💻 第三動：現場追兇——作戰指令與檢驗腳本

身為現場調查員，你必須掌握在 Web 存取日誌中快速撈出 XSS 測試痕跡與識別非法跨站 Referer 的技能。

### 3.1 Linux 現場快篩 Nginx / Apache 存取日誌

#### 步驟 1：一行指令抓出常見 XSS 標籤與事件注入
```bash
# 在 access.log 中篩選 URL 解碼前後的 XSS 特徵
grep -Ei "(<script|%3Cscript|javascript:|onerror=|onload=|document\.cookie|alert\(|<svg|<iframe)" /var/log/nginx/access.log | head -n 25
```

#### 步驟 2：獵殺跨站請求偽造（抓出可疑的第三方 Referer / Origin）
```bash
# 篩選對敏感 API (如 /api/transfer, /user/password) 發起的 POST 請求，且 Referer 不是本站域名的請求
grep -Ei "(POST.*(/transfer|/password|/admin/update))" /var/log/nginx/access.log | \
grep -v "corp.local" | head -n 20
```

### 3.2 Wireshark 封包鑑識過濾器

在捕獲的 Web 流量 PCAP 中，使用以下語法檢出 XSS 注入與跨站請求：

```wireshark
# 1. 篩選所有 URI 或 POST 主體中帶有 JavaScript 執行特徵的請求
http.request.uri matches "(?i)(<script|onerror=|javascript:|<svg)" || (http.request && frame matches "(?i)document\.cookie")

# 2. 檢驗伺服器回應中的 Set-Cookie 是否缺少 HttpOnly (抓出不安全配置)
http.response && (http.set_cookie contains "session" and !(http.set_cookie contains "HttpOnly"))
```

### 3.3 Splunk SPL 異常 XSS 探測分析

#### 偵測情境：大面積 XSS 探測獵捕
> **邏輯**：單一來源 IP 在 10 分鐘內發送超過 15 次包含 HTML/JS 敏感關鍵字的請求，判定為 **自動化 XSS 漏洞掃描器！**

```splunk

| bin _time span=10m
| stats count as xss_attempts, values(uri) as test_payloads by src_ip, uri_path
| where xss_attempts >= 15
| eval Alert_Level="🚨 HIGH: Automated XSS Scanning Activity"
| table _time, src_ip, uri_path, xss_attempts, test_payloads, Alert_Level
```

## ⚖️ 第四動：研判分水嶺——合法富文本 vs 惡意腳本？

在現代 Web 應用中，部落格編輯器、CMS 後台常允許使用者上傳帶有 HTML 格式的文字（富文本 Rich Text，如 `<b>`, `<img>`, `<a>`）。你該如何區分？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | WAF 攔截到 HTML 標籤或 JavaScript 事件處理器，或偵測到未攜帶 CSRF Token 的敏感 POST。 |
| **Q2. 來源實體**（發起請求的使用者是誰？） | 是內部正式員工發佈官方公告（常帶有富文本），還是外部普通未認證使用者？ |
| **Q3. 標籤危險性**（包含哪些具體 HTML 標籤？） | 是安全的排版標籤（`<b>`, `<i>`, `<p>`, `<h1>`），還是高危的可執行標籤（`<script>`, `<svg>`, `<iframe>`, `<object>`）？ |
| **Q4. 事件屬性**（是否攜帶惡意事件監聽器？） | 標籤內是否包含 `onload=`, `onerror=`, `onmouseover=` 等能自動觸發代碼的屬性？ |
| **Q5. 腳本行為**（JavaScript 代碼的意圖為何？） | 代碼是否試圖讀取 `document.cookie`、向外部第三方 IP/域名發起 `fetch()` / `XMLHttpRequest` 傳輸？ |
| **Q6. 跨站來源**（CSRF 請求的來源合法嗎？） | 檢視 HTTP 標頭中的 `Origin` 與 `Referer`：是否嚴格等於本站的完整域名（FQDN）？ |
| **Q7. 橫向波及**（該注入是否已被寫入資料庫？） | 比對資料庫：該惡意字串是否已作為儲存型 XSS 寫入資料庫並呈現在其他使用者畫面上？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 儲存型 XSS：立即從資料庫手動清除該惡意記錄；2. 撤銷可能已洩漏的使用者 Session；3. 部署 CSP 策略。 |

## 🛡️ 第五動：根除與縱深防禦 SOP (Mitigation & Hardening)

防禦 XSS 與 CSRF，必須在前端、後端與 HTTP 安全標頭建立三位一體的防護體系：

### 1. 終結 Session 竊取：強制開啟 `HttpOnly` 與 `Secure`
在伺服器端簽發 Cookie 時，**強制加上 `HttpOnly` 屬性**。這意味著瀏覽器端任何 JavaScript（包含惡意 XSS）**完全無法讀取該 Cookie**！

```http
Set-Cookie: session_id=xyz789; Path=/; Secure; HttpOnly; SameSite=Strict
```

### 2. 徹底終結 CSRF：配置 `SameSite=Strict` 與隨機 Token
- **`SameSite=Strict`**：瀏覽器在任何跨站連線（哪怕是使用者從外部網頁點擊連結進來）**一律不發送此 Cookie**，從物理層面直接斬斷 CSRF！
- **Anti-CSRF Token**：在每個敏感表單中加入一次性隨機 Token，後端驗證失敗則拒絕處理。

### 3. XSS 現代防護金標準：部署 CSP（內容安全原則 - Content Security Policy）
透過 HTTP 回應標頭，強制規定瀏覽器「**只能從哪些合法來源載入腳本，並全面禁止執行內聯 `<script>` 與 `eval()`**」：

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.com; object-src 'none';
```
> 💡 一旦配置了嚴格的 CSP，即使黑客在留言板成功注入了 `<script>alert(1)</script>`，瀏覽器也會**主動拒絕執行它**，並向 SOC 發送違反原則的報警！

## 🎯 靶場實戰檢驗 (Hands-on Lab Walkthrough)

請帶著剛才學到的 XSS 繞過與 CSRF 構造技巧，進入真實靶場：

### 推薦靶場 1：[PortSwigger - Stored XSS into HTML context with nothing encoded](https://portswigger.net/web-security/cross-site-scripting/stored/lab-html-context-nothing-encoded)
- **靶場背景**：部落格留言板功能未對使用者輸入進行任何 HTML 轉義。
- **作戰任務**：
  1. 在留言內容中輸入 `<script>alert(document.domain)</script>` 並送出。

### 推薦靶場 2：[PortSwigger - CSRF vulnerability with no defenses](https://portswigger.net/web-security/csrf/lab-no-defenses)
- **靶場背景**：使用者電子信箱變更功能完全依賴 Cookie，缺少 CSRF Token。
- **作戰任務**：
  1. 登入受害者帳號，攔截更換 Email 的 POST 請求。
  2. 構造一個惡意 HTML 頁面，包含自動送出更換 Email 表單的 JavaScript。
  3. 模擬受害者存取該外部 HTML，驗證受害者的 Email 是否在不知情下被自動竄改。

## 📋 過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能回答，代表你已徹底掌握 XSS 與 CSRF 防禦核心：

- [ ] **Q1**：在跨站腳本攻擊中，**反射型 XSS** 與 **儲存型 XSS** 的最大區別是什麼？為什麼在企業風險評估中，儲存型 XSS 的嚴重程度通常遠高於反射型？
- [ ] **Q2**：為什麼在 Cookie 標頭中加上 **`HttpOnly` 屬性** 能有效防範黑客竊取 Session？加上 `HttpOnly` 之後，XSS 漏洞是否就被徹底消滅了？
- [ ] **Q3**：**CSRF（跨站請求偽造）** 在底層是如何運作的？黑客明明無法讀取受害者的 Cookie，為什麼受害者的瀏覽器卻會聽從黑客的指示完成越權操作？
- [ ] **Q4**：現代瀏覽器 Cookie 的 **`SameSite=Strict` 與 `SameSite=Lax`** 有何關鍵區別？為什麼將敏感 Cookie 設為 `SameSite=Strict` 能從根本上防禦 CSRF？
- [ ] **Q5**：什麼是 **內容安全原則（CSP - Content Security Policy）**？它在瀏覽器層面是如何阻止即使已經被注入進 DOM 的惡意 JavaScript 執行的？
