## 🧩 第一動：底層機制解剖——注入漏洞是如何破壞語法樹的？

注入類漏洞（Injection）常年盤踞 OWASP Top 10 的核心原因，在於**程式設計師將「使用者可控的不可信資料（Data）」與「系統執行的程式代碼（Code）」混淆在同一個字串中動態拼接**。

### 1.1 SQL Injection 的語法樹破壞原理

當後端代碼寫成 `SELECT * FROM items WHERE id = '` + `$userInput` + `'` 時：

```
[正常使用者輸入: 10]
SQL 查詢: SELECT * FROM items WHERE id = '10'
語法樹分析: 條件判定為 [id 等於 10]。

[黑客惡意輸入: 10' OR '1'='1]
SQL 查詢: SELECT * FROM items WHERE id = '10' OR '1'='1'
語法樹分析: 攻擊者的單引號閉合了原本的字串！後面的 OR '1'='1 成為【邏輯判斷運算式】！
結果: 條件永遠為 True，全量資料庫記錄被無條件導出！
```

---

### 1.2 OS Command Injection 的命令鏈接符

當後台系統調用 PHP `system("ping -c 4 " . $_POST['ip'])` 或 Python `os.system()` 時，攻擊者利用作業系統的**命令鏈接符（Command Chaining Operators）**執行額外命令：

```
[常見 Shell 鏈接符]
├── ;   : 無論前一個命令成功與否，依序執行下一個命令 (Linux / Windows)
├── &&  : 僅在前一個命令成功 (Exit 0) 時，執行下一個命令
├── ||  : 僅在前一個命令失敗 (Exit != 0) 時，執行下一個命令 (黑客常故意讓前命令報錯以執行注入)
├── |   : 管道符，將前一個命令的標準輸出作為下一個命令的標準輸入
├── `cmd` 或 $(cmd) : 命令替換符，優先執行括號內命令並將結果替換回原命令列 (Linux)
└── &   : 在背景執行前一個命令，並立即執行下一個命令 (Windows / Linux)
```

---

### 1.3 傳輸層編碼與避雷針（URL Encoding）

攻擊者在 HTTP 請求中不會直接送出空格或單引號，而是透過 URL 編碼（Percent-encoding）傳輸。分析日誌時必須具備「心算解碼」能力：
- `%20` ➔ 空格 ` `（或用 `+` 號代替）
- `%27` ➔ 單引號 `'`
- `%22` ➔ 雙引號 `"`
- `%23` ➔ 井字號 `#`（MySQL 註解符）
- `%2D%2D` ➔ `--`（SQL 註解符）
- `%7C` ➔ 管道符 `|`
- `%26` ➔ 符號 `&`
- `%3B` ➔ 分號 `;`

## 🧭 第二動：解碼意圖——注入特徵與手法速查表

在 Web 存取日誌（Access Log）中，你該如何一眼看出攻擊者正在發動哪一種注入？

### 2.1 注入特徵與攻擊手法速查表

| 日誌與請求特徵現象（看到什麼） | 底層成因與攻擊手法（是什麼攻擊） | 威脅影響與處置優先級（怎麼應對） |
| :--- | :--- | :--- |
| **參數包含 `UNION SELECT`, `CONCAT`, `information_schema`** | **UNION 聯合查詢注入 (UNION-based SQLi)**：<br>攻擊者在同一頁面中拼接另一個 SELECT 查詢，藉由前端頁面回顯直接榨乾整個資料庫結構與帳號資料。 | • **影響**：資料庫全量外洩（P1 級災情）。<br>• **處置優先級**：緊急（立即在 WAF 攔截該參數並通報修補）。 |
| **參數包含 `SLEEP(5)`, `WAITFOR DELAY '0:0:5'`, `pg_sleep()`** | **時間盲注 (Time-based Blind SQLi)**：<br>頁面完全沒有回顯也沒有報錯，黑客利用條件判斷式搭配資料庫延遲函數，逐個字元「盲測」猜解密碼。 | • **影響**：正在進行低頻慢速資料竊取。<br>• **處置優先級**：高（封鎖來源 IP，排查 Web 響應時間 > 5s 的請求）。 |
| **參數包含 `extractvalue(1,...)`, `updatexml()`, `convert(...)`** | **報錯注入 (Error-based SQLi)**：<br>黑客故意傳入引發資料庫 XML 或型別轉換錯誤的函數，讓資料庫把敏感資料隨著錯誤訊息一同吐回前端。 | • **影響**：攻擊者正透過報錯快速提取資料。<br>• **處置優先級**：高（全面關閉生產環境 Web 詳細報錯顯示）。 |
| **參數帶有 `; whoami`, `| dir`, `&& ipconfig`, `; cat /etc/passwd`** | **作業系統命令注入 (OS Command Injection)**：<br>黑客突破應用層，直接在底層 Linux/Windows 作業系統中執行 Shell 命令，準備反彈 Shell 或下載後門。 | • **影響**：主機隨時面臨被奪取 Root/SYSTEM 權限。<br>• **處置優先級**：緊急（立即斷開 Web 服務與外聯連線）。 |
| **User-Agent 或特定 Header 包含 `sqlmap/1.x` 字樣** | **自動化 SQL 注入掃描器探測**：<br>攻擊者使用知名開源工具 sqlmap 進行批量弱點探測與漏洞驗證。 | • **影響**：攻擊者處於自動化掃描偵察階段。<br>• **處置優先級**：中（直接在邊界防火牆將來源 IP 列入黑名單）。 |

## 💻 第三動：現場追兇——作戰指令與檢驗腳本

身為現場調查員，你必須掌握在 GB 級的 Web 日誌中「幾秒鐘撈出注入鐵證」的技能。

### 3.1 Linux 現場快篩 Nginx / Apache 存取日誌

#### 步驟 1：一行正則掃描出所有 SQL 注入請求（UNION, 註解, SLEEP）
```bash
# 在 access.log 中篩選 URL 解碼前後的 SQL 注入特徵
grep -Ei "(union.*select|select.*from|sleep\(|waitfor.*delay|load_file|information_schema|benchmark\()" /var/log/nginx/access.log | head -n 20
```

#### 步驟 2：獵殺命令注入（管道符號、分號、反引號、危險系統指令）
```bash
# 篩選帶有 whoami, /etc/passwd, ping, curl 拼接特徵的請求
grep -Ei "(%7C|\||%26|&|%3B|;).*(whoami|cat\s|nc\s|curl|wget|dir|ipconfig|ls\s)" /var/log/nginx/access.log | head -n 20
```

#### 步驟 3：統計攻擊最猖獗的來源 IP 與受攻擊的 API 端點
```bash
# 提取發起注入次數最多的前 10 名公網 IP
grep -Ei "(union.*select|sleep\(|%27.*or.*1=1)" /var/log/nginx/access.log | \
awk '{print $1}' | sort | uniq -c | sort -nr | head -n 10
```

### 3.2 Wireshark 封包鑑識過濾器

在捕獲的 Web 流量 PCAP 中，使用以下語法精確過濾：

```wireshark
# 篩選所有 URI 或 POST 內容中帶有常見注入關鍵字的 HTTP 封包
http.request.uri matches "(?i)(union.*select|sleep\(|waitfor|\bor\b.*1=1)"

# 篩選命令注入特徵（管道符與系統命令）
http.request.uri matches "(?i)(whoami|cat%20/etc|cmd\.exe)"

# 觀察伺服器回傳 500 內部錯誤的請求（報錯注入常態）
http.response.code == 500
```

### 3.3 Splunk SPL 注入威脅分析

#### 偵測情境：時間盲注偵測（Web 響應時間異常飆高）
> **邏輯**：當單一來源 IP 連續發送帶有 SQL 關鍵字的請求，且伺服器回應耗時（`response_time`）精準大於 5 秒，判定為 **時間盲注進行中！**

```splunk
index=web_access (uri="*sleep*" OR uri="*waitfor*")
| eval duration_sec=tonumber(response_time)
| where duration_sec >= 5
| stats count, values(uri) as test_payloads by src_ip, uri_path
| where count >= 3
| eval Alert_Level="🚨 HIGH: Time-based Blind SQLi Detected"
| table src_ip, uri_path, count, test_payloads, Alert_Level
```

## ⚖️ 第四動：研判分水嶺——正常業務文字 vs 惡意注入？

在日常業務中，使用者在留言板輸入引號、搜尋包含 `&` 的商品名稱（如 `AT&T`）、或輸入英文姓名（如 `O'Connor`）也會包含特殊字元。你該如何區分？

### 4.1 SOC 8 大黃金研判問題對照表

| 核心提問（研判維度） | 本技術點實戰檢核標準 |
| :--- | :--- |
| **Q1. 觸發原因**（為何會發出此警報？） | WAF 觸發 SQLi/CMDi 規則攔截，或 Web Access 日誌匹配到注入正則。 |
| **Q2. 來源實體**（發起請求的 IP 是誰？） | 是內部員工正常的內部 IP、合作夥伴 API，還是來自未知名公網、匿名代理或 Tor 節點？ |
| **Q3. 參數上下文**（觸發的輸入欄位是什麼？） | 是搜尋引擎、留言板（易誤報），還是隱藏在背景的 `id=`、`cat_id=`、`order_by=` 等數值型參數？ |
| **Q4. 結構破壞性**（參數是否具備語法閉合特徵？） | 單純有 `'` 是誤報；若引號後面**緊跟著 SQL 邏輯運算子（`OR`, `AND`, `UNION`）與註解符（`--`, `/*`, `#`）**，必為惡意！ |
| **Q5. 工具特徵**（是否有自動化工具指紋？） | User-Agent 是否包含 `sqlmap`, `nikto`, `curl`？請求頻率是否呈現每秒數十次的高頻掃描？ |
| **Q6. 攻擊成果**（攻擊是否已經得逞？） | 檢視 Web 響應碼（HTTP Status）：是返回 403 (被 WAF 攔截)、500 (報錯失敗)，還是返回了 **200 OK 且 Response 酬載異常巨大**（資料庫全量吐出）？ |
| **Q7. 橫向波及**（該 IP 是否還在探測其他頁面？） | 檢視該 IP 的存取歷史：是否在全站漫遊遍歷所有 URL 參數？ |
| **Q8. 處置動作**（下一步是什麼？） | 1. 若為 200 成功外洩：立即下線該脆弱 API 端點、啟動資料洩漏應變；2. 若為未遂掃描：於邊界防火牆將攻擊 IP 封鎖 24 小時。 |

## 🛡️ 第五動：根除與縱深防禦 SOP (Mitigation & Hardening)

防禦注入漏洞，任何前端過濾都是紙糊的。必須在架構層面落實以下三道根本防線：

### 1. 唯一根本防禦：參數化查詢 (Prepared Statements / Parameterized Queries)
徹底將「代碼」與「數據」分離。資料庫引擎預先編譯 SQL 語法樹，使用者傳入的任何內容**永遠只會被當作純文字參數處理**，絕不可能改變語法邏輯！

```php
// ❌ 致命錯誤：直接字串拼接 (SQLi 溫床)
$sql = "SELECT * FROM users WHERE email = '" . $_POST['email'] . "'";

// ✅ 正確做法：PDO 預編譯參數化查詢 (徹底免疫 SQLi！)
$stmt = $pdo->prepare('SELECT id, password FROM users WHERE email = :email');
$stmt->execute(['email' => $_POST['email']]);
$user = $stmt->fetch();
```

### 2. 命令注入根除：嚴禁使用系統 Shell，採用陣列參數化調用
在呼叫外部程式時，**嚴禁傳遞給系統 Shell 直譯器**（避免使用 `system()`, `exec()`, `shell_exec()` 或 `eval()`）：

```python
# ❌ 致命錯誤：shell=True 會喚起 /bin/sh，允許管道符鏈接
subprocess.Popen(f"ping -c 1 {user_ip}", shell=True)

# ✅ 正確做法：shell=False，以陣列形式傳入參數，作業系統不會解釋任何 ; 或 |
subprocess.Popen(["ping", "-c", "1", user_ip], shell=False)
```

### 3. 資料庫最小特權原則 (Least Privilege)
- Web 應用程式所連接的資料庫帳號，**嚴禁給予 `DBA` 或 `root` 特權**！
- 嚴格撤銷該帳號的檔案讀寫權限（如 MySQL 的 `FILE` 權限，防止黑客執行 `SELECT ... INTO OUTFILE` 寫入 WebShell）。

## 📋 過關驗收檢查點 (Mastery Checklist)

不看筆記，試著回答以下 5 個實戰問題。若都能回答，代表你已徹底掌握 Web 注入防禦核心：

- [ ] **Q1**：為什麼在防禦 SQL 注入時，使用 JavaScript 在前端瀏覽器過濾單引號與特殊字元，在黑客眼中「完全等同於沒有防禦」？
- [ ] **Q2**：什麼是 **參數化查詢（Prepared Statements）**？在資料庫引擎底層，它為什麼能從根本上 100% 杜絕 SQL 注入的發生？
